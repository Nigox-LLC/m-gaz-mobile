# AGENT.md

This file gives Codex and other coding agents repository-specific operating rules. Keep it aligned with `CLAUDE.md`.

## First Steps

1. Start from `dev` unless the user explicitly names another branch.
2. Check `git status --short --branch` before changing files.
3. Read the relevant code before planning or editing.
4. Keep the change scoped to the issue.
5. Never stage unrelated files silently.

## Commands

```bash
flutter pub get
flutter test
flutter test path/to/file_test.dart
flutter analyze
dart run build_runner build --delete-conflicting-outputs
```

Run build runner only when DI annotations or generated injectable wiring changed.

Current analyzer baseline: 11 info-level diagnostics, 0 errors. Do not increase it. If `flutter analyze` exits non-zero only because of that baseline, say so clearly.

## Architecture Guardrails

The project has both legacy and clean-architecture code.

- New clean stack: `lib/features/<feature>/{data,domain,presentation}`.
- Legacy stack: `lib/ui`, `lib/core/api`, `lib/core/models`, `lib/di.dart`.
- Do not move a feature between stacks unless the task is a migration.
- In clean architecture, keep `domain` free of Flutter, Dio, data models, Hive, and API clients.
- Keep generated files, especially `lib/app/injection.config.dart`, generated by tooling.

## Date And Time Rules

Visible UI date/time formats are fixed:

- Date: `dd.MM.yyyy`
- Time: `HH:mm:ss`
- Date + time: `dd.MM.yyyy HH:mm:ss`

Use `AppDateFormatter` from `lib/core/utils/app_date_formatter.dart` for user-facing text. Use `dateFromString` and `dateTimeFromString` for string values returned by APIs.

Do not add new user-facing:

- `DateFormat(...)` in screens/widgets
- `DateTime.toString().substring(...)`
- manual date/time string assembly with `padLeft(...)`

Do not change API/storage wire formats such as ISO strings, route timestamps, or backend `yyyy-MM-dd` fields unless the API contract changes.

## UI Work

- Use existing project widgets and styles where possible.
- Preserve business logic unless the issue explicitly includes logic changes.
- Check responsive behavior, long text, loading/empty/error states, and overflow risks.
- Avoid unrelated redesigns while fixing a narrow bug.

## Tests And Verification

Choose tests based on the touched code:

- Date/time formatter changes: `flutter test test/core/utils/app_date_formatter_test.dart`
- Translation key changes: `flutter test`
- General changes: `flutter test`
- Before PR: `flutter analyze`

For date/time audits, also run:

```bash
rg -n 'DateFormat\(|toString\(\)\.substring|dd MMM|HH:mm|padLeft\(2' lib test
```

Remaining matches should be central formatter, tests, comments, or non-user-facing helpers.

## GitHub Workflow

1. Branch from `dev` with `codex/<topic>`.
2. Commit only scoped files.
3. Push the branch.
4. Open PR to `dev`.
5. Use `Closes #N` only when the issue should close on merge.
6. After merge, verify PR state, issue state, current branch, and clean worktree.
